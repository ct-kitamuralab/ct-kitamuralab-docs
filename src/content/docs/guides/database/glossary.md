リレーショナルDBで使う用語を分類別にまとめています。SQLの記法に触れる例はSQLite向けです。

## 基本構造

### テーブル

同じ種類のデータを行と列で保存する表。例えば、`weather_stations` は観測地点を保存するテーブルです。

### 行（レコード）

テーブルに保存する1件のデータ。地点表なら、1つの地点が1行です。

### 列（カラム）

テーブルのデータ項目。地点表の `id`・`code`・`name` は、それぞれ列です。

### スキーマ

テーブル、列、型、制約など、DBの構造の定義。DB製品によっては、テーブルなどをまとめる名前空間を指すこともあります。

### データ型

整数・文字列など、値の種類。SQLiteの `INTEGER` は整数、`TEXT` は文字列、`REAL` は浮動小数点数です。

### NULL

値がない、または不明であることを表すもの。0や空文字 `''` とは異なります。SQLでは `= NULL` ではなく `IS NULL` で調べます。

## キー・制約

### 主キー

行を一意に識別するために選んだ列、または列の組み合わせ。SQLでは `PRIMARY KEY` で指定します。

### 候補キー

行を一意に識別でき、余分な列を含まない列の組み合わせ。候補キーのうち1つを主キーとして選びます。

### 複合キー

複数列で構成するキー。例えば「地点ID＋観測日時」で1件の観測を識別する場合です。

### 外部キー

別のテーブルなどの主キー・一意キーを参照する列、または列の組み合わせ。SQLでは `REFERENCES` で参照先を指定します。

SQLiteでは、外部キーの制約を適用するために、接続ごとに `PRAGMA foreign_keys = ON;` で有効化します。

### NOT NULL

`NULL` の保存を禁止する制約。空文字 `''` は禁止しません。

### UNIQUE

値、または値の組み合わせの重複を禁止する制約。SQLiteでは `NULL` 同士は重複と扱わないため、必須項目には `NOT NULL` も指定します。

### CHECK

保存する値の条件を定義する制約。`CHECK (humidity_percent BETWEEN 0 AND 100)` は、湿度を0〜100の範囲に限定します。SQLiteでは条件の結果が `NULL` の場合も保存を許します。

### 参照整合性

参照する行と参照先の行の対応が矛盾しないこと。例えば、存在しない地点IDを観測の参照先にしないことです。外部キーの制約で守ります。

## 検索・集計

### SELECT

データを取得するSQL。`SELECT id, name FROM weather_stations;` は地点表からIDと名前を取得します。

### WHERE

対象の行を条件で絞る句。`WHERE id = 1` はIDが1の行を対象にします。検索だけでなく更新・削除にも使います。

### ORDER BY

検索結果の並び順を指定する句。`ASC` は昇順、`DESC` は降順です。`ORDER BY` を省略すると、結果の順序は保証されません。

### GROUP BY

同じ値を持つ行をグループにまとめる句。地点IDでまとめて、地点ごとの件数や平均を求める場合などに使います。

### HAVING

集計後のグループを条件で絞る句。`WHERE` が集計前の行を絞るのに対し、`HAVING` は集計結果に条件を付けます。

### 集計関数

複数行から件数・合計・平均などを求める関数。`COUNT(*)` は行数、`SUM(列)` は合計、`AVG(列)` は平均を求めます。`COUNT(列)`・`SUM`・`AVG` は `NULL` を除いて計算します。

### JOIN

条件に対応する行を組み合わせて、複数のテーブルから結果を取得する操作。内部結合（`INNER JOIN`）は対応する行だけを返し、左外部結合（`LEFT JOIN`）は対応がない左側の行も残します。

### サブクエリ

SQL文の中に書く別の検索SQL。別の検索結果を絞り込み条件や取得元にする場合などに使います。

### ビュー

検索SQLに名前を付け、テーブルのように参照できるようにしたもの。SQLiteのビューは、検索結果そのものを保存するものではありません。

## データ変更

### INSERT

行を追加するSQL。`INSERT INTO` で追加先を指定し、`VALUES` で保存する値を指定できます。

### UPDATE

行の値を変更するSQL。`SET` で変更する列と値を指定します。

### DELETE

行を削除するSQL。テーブルの定義は残ります。

`UPDATE` と `DELETE` は `WHERE` を省略すると全行が対象です。

### UPSERT

追加を試み、キーが重複した場合などに既存行を更新する処理。SQLiteでは `INSERT ... ON CONFLICT ... DO UPDATE` で指定します。外部キーやすべての制約違反を処理するものではありません。

## 設計

### 正規化

データの依存関係に基づいてテーブルを整理する設計手法。同じ事実を複数箇所で別々に管理することによる、不整合を防ぐために使います。

### 非正規化

検索・集計などの目的で、正規化された構造に重複する値などを持たせる設計。読み取り時の処理を減らせる場合がありますが、元データとの一致を保つ仕組みが必要です。

### 関数従属性

ある値が決まると、別の値も一意に決まる関係。例えば、地点IDから地点名が1つに決まる関係です。たまたま保存済みの行が同じ値かではなく、データの仕様で判断します。

### ER図

データの種類と、それらの関係を表す図。テーブルの設計では、キーや「1対多」などの対応関係を示します。ERはEntity Relationshipの略です。

### 1対多

1件のデータに、複数のデータが対応する関係。1つの地点に複数時刻の観測が対応する場合などです。

### 多対多

両側のデータが、それぞれ複数の相手に対応する関係。例えば、1つの記事に複数のラベルが付き、1つのラベルも複数の記事に付く場合です。

### 中間テーブル

多対多の対応を保存するテーブル。記事とラベルなら、記事IDとラベルIDの組み合わせを1行ずつ保存します。

## 性能

### インデックス

データの検索を高速化するための構造。対象の行を探す際に利用されます。保存容量が増え、追加・更新・削除時にはインデックスを維持する処理も必要になります。

### 複合インデックス

複数列で構成するインデックス。列の順序によって適した検索が異なります。例えば「地点ID・観測日時」の順なら、地点を指定した日時範囲の検索に利用できます。

### 全表走査

テーブルの全行を調べる処理。フルテーブルスキャンとも呼びます。少量のデータや大部分の行を取得する検索では、適切な処理になる場合もあります。

### 実行計画

DBがSQLを処理する方法。どのテーブルやインデックスを読むかなどを確認できます。SQLiteでは `EXPLAIN QUERY PLAN` を検索SQLの前に付けて表示します。

## データ保護・同時処理

### トランザクション

一連の操作をまとめて確定・取り消しする単位。SQLiteでは `BEGIN` で開始し、`COMMIT` で確定、`ROLLBACK` で取り消します。

### COMMIT

トランザクションの変更を確定するSQL。

### ROLLBACK

未確定のトランザクションの変更を取り消すSQL。確定済みの変更を戻す操作ではありません。

### ACID

トランザクションの性質を表す4つの頭文字。原子性・一貫性・分離性・永続性を指します。

<details>
<summary>補足：ACIDの4つの性質</summary>

- **原子性（Atomicity）**：一連の変更を、すべて適用するか、すべて取り消す。
- **一貫性（Consistency）**：定義した制約など、データの整合性を守る。
- **分離性（Isolation）**：同時に実行する処理が互いに干渉する範囲を制御する。具体的な保証は分離レベルで異なる。
- **永続性（Durability）**：確定した変更を、障害後も保持する。

</details>

### ロック

同じデータへの操作が競合しないよう、アクセスを制御する仕組み。SQLiteでは同じDBへの書き込みを同時に1つずつ処理します。

### バックアップ

障害や誤操作に備えて、データを復元できるコピーを保存すること。SQLiteの `sqlite3` では `.backup` を使えます。使用中のDBは更新内容が別ファイルにある場合があるため、DBファイルだけをそのままコピーすると不完全になることがあります。
